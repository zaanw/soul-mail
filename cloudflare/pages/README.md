# Предпочтительный адрес сайта: soul.pages.dev

Имя `soul` — пожелание пользователя. Конфигурация не подтверждает доступность или владение `soul.pages.dev`. Это проверяется в Cloudflare при создании Pages-проекта и по фактически назначенному полю `subdomain`. Наличие или отсутствие DNS-записи не доказывает доступность имени.

Этот маленький Pages-проект передаёт все запросы в уже подготовленный Next.js Worker `soul-mail` через приватный service binding `SOUL_MAIL`. Он сохраняет URL, Origin, тело запроса, cookies и Set-Cookie ответа, поэтому регистрация и почтовый ящик остаются на одном публичном адресе. Само приложение и PostgreSQL продолжают работать в Worker/Hyperdrive. Публичный HTTP-прокси здесь не создаётся: адрес назначения задаётся только серверным binding.

Для публикации Pages используйте токен с правом **Cloudflare Pages: Edit** для выбранного аккаунта; права основного Worker при этом остаются отдельными.

После подключения доступа к Cloudflare:

1. Убедитесь, что доступен именно `soul.pages.dev`. Создайте Pages-проект `soul` только в своём аккаунте и проверьте фактически назначенный адрес. Если Cloudflare предлагает другое имя/суффикс, не считайте желаемый адрес полученным.
2. Для уже подготовленного Worker настройте Hyperdrive и миграции базы по корневому `CLOUDFLARE.md`. Только после подтверждения адреса установите `CF_APP_URL=https://soul.pages.dev` в приватных настройках его публикации. Это задаст канонический Origin для CSRF и ссылок восстановления. Не ставьте этот адрес в работающем production до подготовки переключения.
3. Опубликуйте Worker `soul-mail`. Если выбрано другое имя Worker, измените `service` в этой конфигурации.
4. Опубликуйте Pages-проект из корня репозитория:

   ```sh
   npm run deploy:pages
   ```

   Команда требует существующего Pages-проекта и авторизации Wrangler. Она не проверяет глобальную доступность имени и не создаёт базу данных. Service binding берётся из `cloudflare/pages/wrangler.jsonc`. Если аккаунт использует защищённые preview-окружения, настройте их binding отдельно перед preview-публикацией.

5. Проверьте на фактически назначенном адресе `/api/health`, регистрацию, вход, внутреннюю доставку и выход. Только после этой проверки можно сообщать, что сайт опубликован на желаемом адресе.

Если настраиваете этот Pages-проект через GitHub в панели: корневая директория — `cloudflare/pages`, output directory — `public`, сборка для этого шлюза не нужна. Это **дополнительный Pages-проект**, а не замена сборки существующего Worker. В настройках Pages обязателен service binding `SOUL_MAIL` → Worker `soul-mail`.

`soul.pages.dev` — адрес сайта, а не автоматически доступный домен внешней электронной почты. Управлять MX/SPF/DKIM для зоны `pages.dev` проект не может. Для внешней почты требуется отдельный контролируемый домен и провайдер. Workers Paid по-прежнему нужен для CPU-бюджета Argon2id в основном приложении.
