# SOUL MAIL на Cloudflare Workers

Проект адаптирован под **Cloudflare Workers через OpenNext**, а не статический Cloudflare Pages. PostgreSQL и формат существующих паролей сохранены. Сборка и работа приложения проверяются в локальном `workerd`.

Публичная публикация требует вашего аккаунта Cloudflare и доступной из интернета базы PostgreSQL. Локальная Docker-база из облачной среды не является публичным сервером базы данных. Адаптация к Workers сама по себе не означает, что приложение уже опубликовано.

## Подготовленная инфраструктура

- Next.js 16 + OpenNext, `nodejs_compat`, заранее собранный WASM-компилятор Prisma.
- PostgreSQL через Hyperdrive; отдельный Prisma-клиент и пул на запрос, закрытие соединений через `waitUntil`.
- Переносимый Argon2id (`@noble/hashes`): 64 МиБ, 3 итерации, 1 линия; прежние PHC-хеши остаются действительны. Параллельное выделение памяти для хеширования ограничено очередью.
- HTTPS-почта через Resend. Нативный SMTP остаётся доступным при запуске на Node.js, в Worker он отключён.
- Проверка TXT-записей через DNS-over-HTTPS внутри Worker.
- Общий кэш писем и аккаунтов не используется. R2/KV для этой конфигурации не нужны.

Нужен **Workers Paid**: в конфигурации установлен CPU-бюджет 30 секунд, а Argon2id требует существенно больше 10 мс бесплатного тарифа. Скрипт не покупает тариф и не меняет платёжные настройки аккаунта. Размер сжатого Worker проверяется `npm run check:cloudflare`; локальный тест не подтверждает реальные лимиты и задержки публичного окружения.

## 1. PostgreSQL и Hyperdrive

1. Создайте отдельную PostgreSQL-базу приложения у выбранного провайдера. Включите TLS, резервные копии и ограничьте доступ необходимыми ролями.
2. Примените `npm run db:migrate` из доверенного окружения, где `DATABASE_URL` указывает именно на эту новую базу приложения. Секрет подключения задаётся приватно; не копируйте пример пароля и не отправляйте его в чат. Команда публикации миграции не выполняет.
3. В Cloudflare → Hyperdrive создайте конфигурацию подключения к этой базе. Для SOUL MAIL **отключите query caching**. Иначе проверки сессий, отключённых аккаунтов и новые письма могут получать устаревшие данные.
4. Сохраните Hyperdrive ID. Production Worker получит подключение через binding `HYPERDRIVE`, пароль базы в код и публичные переменные не попадает.

Команда Wrangler для создания конфигурации поддерживает `--caching-disabled=true`. Безопаснее ввести подключение в защищённой форме Cloudflare, чем помещать пароль в командную строку. Скрипт публикации проверяет через API, что query caching действительно отключён, и останавливается до загрузки Worker, если это не так.

## 2. Доступ и адреса

Скопируйте `.env.cloudflare.example` в **игнорируемый** `.env.cloudflare` или задайте параметры через защищённые настройки среды/CI:

| Параметр                | Назначение                                                                                                                                                                 |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `CLOUDFLARE_API_TOKEN`  | Приватный токен с доступом к выбранному аккаунту: Workers Scripts Edit и Hyperdrive Read; дополнительные права Wrangler должны соответствовать настройкам аккаунта.        |
| `CLOUDFLARE_ACCOUNT_ID` | Account ID вашего аккаунта.                                                                                                                                                |
| `CF_HYPERDRIVE_ID`      | ID конфигурации Hyperdrive из предыдущего шага.                                                                                                                            |
| `CF_APP_URL`            | Точный HTTPS origin приложения: адрес из вашего Workers dashboard или собственный домен. Без пути и query string.                                                          |
| `CF_MAIL_DOMAIN`        | Домен почтовых адресов. Для внутренней переписки допустим назначенный hostname Worker; для внешней почты нужен домен, который вы контролируете и подтвердили у провайдера. |
| `CF_WORKER_NAME`        | Имя Worker, по умолчанию `soul-mail`. Выберите другое, если это имя занято чужим приложением в вашем аккаунте.                                                             |

`CF_APP_URL` и `CF_MAIL_DOMAIN` отделены от локальных `APP_URL` и `MAIL_DOMAIN`, чтобы подготовка публикации не меняла настройки dev-сервера. Скрипт преобразует их в runtime-переменные Worker.

Для получения адреса используйте реальный Workers subdomain своего аккаунта. Пример формата — `https://<worker>.<your-account-subdomain>.workers.dev`; пример не является готовым адресом. `soul.page.dev` не предполагается доступным или принадлежащим проекту. Для собственного домена настройте маршрут в Cloudflare и используйте его в `CF_APP_URL`.

## 3. Сборка и публикация

```sh
npm ci
npm run db:generate
npm run build:cloudflare
npm run check:cloudflare
npm run deploy:cloudflare
```

`build:cloudflare` создаёт `.open-next/worker.js` и `.open-next/assets`. `check:cloudflare` выполняет Wrangler dry-run и ничего не публикует. При необходимости можно проверить именно production-конфигурацию: `npm run deploy:cloudflare -- --dry-run` после заполнения её несекретных параметров.

`deploy:cloudflare`:

- Проверяет обязательные настройки, HTTPS origin и Hyperdrive query caching.
- Создаёт приватную `.local/wrangler.deploy.json` с правильным binding и self-reference.
- Вызывает Wrangler для выбранного аккаунта и Worker.
- При наличии передаёт `RESEND_API_KEY` и `INBOUND_TOKEN` через stdin команды `wrangler secret bulk`; значения не записываются в public vars и не выводятся скриптом.

Команда может обновить существующий Worker с выбранным именем. Она не создаёт PostgreSQL, не мигрирует базу и не меняет DNS. Если загрузка runtime-секретов завершится ошибкой после публикации кода, исправьте ошибку и повторите команду; не считайте внешний почтовый канал подключённым до проверки.

После публикации проверьте `/api/health`, регистрацию, вход, отправку письма второму аккаунту, смену пароля и завершение сессий. `APP_URL` должен точно совпадать с адресом в браузере, иначе CSRF-проверка отклонит изменения. До этого публичная работоспособность не подтверждена.

## 4. Внешняя почта

Укажите приватный `RESEND_API_KEY` и публичный `MAIL_FROM`, соответствующий подтверждённому отправителю. Для отправки с пользовательских адресов подтвердите основной и подключаемые домены у Resend. Настройте провайдерские DNS-записи SPF/DKIM/DMARC. Успешный ответ Resend означает принятие провайдером, а не подтверждённую доставку адресату.

Входящая почта использует существующий защищённый `/api/mail/inbound`; настройте адаптер шлюза, проверяющий подпись выбранного провайдера и передающий нормализованный JSON. Сырые webhook-события Resend или Cloudflare Email Routing нельзя просто направить в этот endpoint без адаптера формата и проверки подлинности. Внешние провайдеры и публичные DNS в локальной проверке не подменяются и не считаются подключёнными.

## Локальная проверка Worker

```sh
node scripts/dev-db.mjs
npm run db:generate
npm run db:migrate
npm run build:cloudflare
npm run preview:cloudflare
```

Помощник preview создаёт приватную `.dev.vars` из существующей локальной `.env`, если файла ещё нет. Чужой `.dev.vars` не перезаписывается. По умолчанию используются порт 8787 и локальная PostgreSQL. Серверные секреты не нужно вводить в публичные настройки Wrangler.

```sh
npm run typecheck
npm test
npm run test:cloudflare
```

`test:cloudflare` создаёт **новую отдельную локальную базу**, применяет миграции, запускает workerd на порту 8788 и выполняет все 6 E2E-сценариев. Основная dev-база, её данные и лимиты не сбрасываются. Удалённые базы этот помощник отклоняет. Тестовые базы оставляются для диагностики; их можно удалить отдельно после проверки. Проверяются реальные PostgreSQL-транзакции, доступ к письмам/вложениям, одноразовые токены, входящий шлюз, администратор, desktop и мобильный интерфейс. HTTP-почтовый транспорт проверяется изолированными тестами с подменённым `fetch`; реальных писем наружу тест не отправляет.

Зависимости `glob` и `minimatch` инструментов OpenNext закреплены на исправленных версиях через `overrides`. После обновления адаптера повторяйте сборку, dry-run и Worker E2E.
